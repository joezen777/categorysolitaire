# Dynamic visual gameplay harness — requirements

Status: implementation plan only, prepared 2026-10-14. The changes in this planning commit do not implement a new harness, start an AWS/browser/model session, play games, provision infrastructure, or publish evaluation results.

## Objective

For any completed Category Solitaire branch iteration, evaluate its exact deployed build through the visible UI and produce an auditable report of ten independent games: how many were won, how many had confirmed rule violations, which illegal actions the app accepted, which legal actions the app blocked, and what other bugs were observed. Reuse the same evaluator across different layouts and generated implementations without per-branch selectors, source imports, or hidden-state access.

The primary output is observed behavior with replayable evidence. A visual agent failing to solve a partially observed deal is not proof that the game is unwinnable. A win banner alone is not proof that the game was won legally. The report must make these distinctions explicit.

Important gaps to fix before using results as a benchmark:

- Loose win parsing accepts text such as `incomplete`, `drawing`, `not_won`, or the string `"false"` as success. Unknown counters can become zero.
- The same model proposes a move, judges legality, interprets progress, and declares victory. Its self-report is not an independent verdict.
- Compressed PNG byte differences and action descriptions influence reward/progress; an unchanged image after a missed drag can be scored as successful rule enforcement.
- Solve/mechanics can stop the whole episode loop after one win/blocked game. `--episodes 10` is not the requested ten-game evaluation.
- Every mode learns/saves a shared policy, the seed includes run time, reload retains browser storage, and mobile dragging uses mouse input. Phone dimensions are not reliably selected by `--mobile`.
- Errors can lose the report; runtime console/network errors are not collected; retries, total duration, and model spend lack complete bounds. Existing branch URLs are a fixed list.

Source locations and remediation tasks are mapped in [tasks.md](tasks.md). Preserve useful pieces; introduce a separately named evaluation mode/entry point so exploratory training remains clearly labeled.

## RQ-1: Dynamic targets and immutable identity

1. Accept an explicit HTTP(S) game URL or a target manifest generated by the build/deployment pipeline. Each target includes branch/ref, full source SHA, deployment/build ID, bundle digest when available, URL, and external deck/rules version.
2. Resolve a branch once at run start. Verify readiness and build identity before playing; abort with `target_mismatch` if deployment changes. Do not infer the target from a branch-name-to-hostname convention or accidentally test the comparison dashboard.
3. A new completed branch requires configuration/manifest data only, not a new harness code path, selector map, card component import, or generator-side hook. Plan-only experiment branches are `not_ready`, not broken games.
4. A URL without a verifiable source/build receipt may be explored but must be labeled `unverified_build` and excluded from the primary cross-branch comparison.
5. The harness and oracle live on main and measure app variants externally. Do not merge main, evaluator scripts, or test dependencies into game branches.

## RQ-2: Interchangeable browser execution

1. Provide a local Playwright backend and an AgentCore Browser backend behind the same observation/action/lifecycle contract.
2. The AWS route uses the named CLI/SDK profile `opensearchprod`; its locally configured region is `us-east-1`. Profile existence and local CLI request-schema support were checked, not AWS authorization, service quotas, model access, or live connectivity.
3. Treat AgentCore as browser infrastructure. A separately configured, pinned vision/planning model still observes the screenshots and selects moves. Browser credentials do not configure or authorize that model automatically.
4. Cloud sessions need a reachable deployed URL or approved private-network route. A localhost address on the developer machine is not reachable from a public AgentCore session; use the local backend for that URL.
5. Isolate every normal game in a fresh local browser context or fresh AgentCore session. No saved browser profiles, storage reuse, shared learned policy, or cross-target agent memory in evaluation mode.
6. Always persist terminal evidence and attempt session cleanup, including on launch/navigation/model failure, cancellation, timeout, and interrupted report generation. Record cleanup failures separately and provide an explicit session-ID cleanup path.

## RQ-3: Visible observation and reliable input

1. Observe screenshots, visible text/OCR, layout, and action history. The primary benchmark is visual-only. Do not read app source, React stores, hidden DOM attributes, network deck payloads, local storage, or browser-side game functions.
2. Track cards and regions with confidence, bounding boxes, screenshot references, and unknown fields. Infer unknown identities only as hypotheses; do not convert them to observed facts. The external expected deck is a rules fixture, not evidence of a hidden card's location.
3. Support mouse drag, real synthesized touch drag, tap, tap-to-move, scrolling, keyboard controls, wait, and navigation. Map screenshot pixels to CSS coordinates using the actual viewport/DPR/scroll position; reject malformed coordinates instead of silently clamping them into unrelated controls.
4. Prove the source card was selected/picked up and the intended destination reached before treating a failed transition as game rejection. Capture gesture-time evidence for drag return, group motion, and completion effects.
5. Wait for stable board observations with a bounded deadline; decorative animation must not count as progress. Decode PNGs before comparing pixels and compare aligned relevant regions, not compressed bytes. Pixels support, but never determine, legality.
6. Preserve the actually tested browser/input modality. A narrow Chromium viewport is not a real mobile Safari test; a mouse drag is not a touch drag. Report unavailable modalities separately.

## RQ-4: Independent rule adjudication

1. Implement a deterministic oracle over externally specified rules and confidence-qualified observations/history. For each action, return `LEGAL`, `ILLEGAL`, or `UNKNOWN`, then compare the observed transition with allowed outcomes.
2. Keep perception, planner, actuator, oracle, and report aggregation separate. A planner's expected result or confidence cannot certify its own action.
3. Cover every product requirement in [rule-catalog.md](rule-catalog.md), including draw/recycle ordering, title/item/group moves, reveal, foundation progress/clearing, scoring once, invalid rollback, controls, and terminal state.
4. Distinguish `illegal_action_accepted`, `legal_action_blocked`, `incorrect_transition`, `premature_win`, and other observed bugs. Track app defects separately from perception, planning, input delivery, infrastructure, and unresolved-rule interpretation errors.
5. If the agent attempted an illegal move and the app accepted it, record both the agent mistake and the app enforcement defect. If the app rejected it correctly, do not report a blocked legal move.
6. Confirm defects only with sufficient before/after evidence, known preconditions, successful actuation, and a reproducible trace or strong deterministic event evidence. Keep low-confidence findings suspected or inconclusive; preserve reviewer decisions separately.
7. Preserve five canonical rule statuses: PASS, FAIL, UNKNOWN, NOT_EXERCISED, and NOT_OBSERVABLE, with opportunity and attempt counts. Friendly UI labels are pass, fail, inconclusive, untested, and not observable respectively. Zero observed failures is not “all rules passed.” Unreachable scenarios remain untested.
8. Clarify the original prompt's ambiguities in the versioned oracle contract before comparison. Do not report ambiguous behavior as a confirmed defect by silently selecting one interpretation.

## RQ-5: Ten-game evaluation and separate rule probes

1. Allocate exactly ten normal-game slots per target SHA and run configuration. Produce ten terminal rows even if the app, model, or cloud fails. Do not stop the batch after the first win or replace failed trials with hidden successful retries.
2. Use a fixed, published schedule with five desktop and five mobile-view games, explicit input modes, the same evaluator version/model/budgets, and independent episodes. Aggregate and show modality strata separately.
3. The normal-game agent attempts legal play to completion. A separate probe suite deliberately tests illegal and boundary actions in isolated probe sessions. A probe that corrupts the board must not create a “win” in the ten-game numerator.
4. Record the terminal outcome enum from rule-catalog.md, win evidence, confirmed violations, blocked legal actions, unknowns, and exact stop reason. Outcome counts sum to ten; overlapping defect counts are labeled as such.
5. A verified legal win requires visible terminal evidence plus a consistent completion/card ledger for the declared deck and no confirmed illegal transition used to reach that win. Record wins with violations and unverified win claims separately.
6. Two recycle cycles without progress or an empty model candidate list means policy exhaustion/no-progress, not a proof of unsolvability. Try bounded alternative observations/candidates, then stop inconclusively if needed.
7. Evaluation is frozen: no reinforcement learning, no policy saves, deterministic agent RNG independent of timestamps, no automatic model switching, and no heuristic-click fallback after model failure. Training is a separate dataset/mode and is excluded from benchmark reports.
8. Per-game default planning envelope: at most 20 minutes of active gameplay, a 25-minute wall-clock deadline from session allocation (including pauses/setup), 1,500 executed actions, and 1,600 model calls; per-model-call timeout 60 seconds and at most two retries. Declare token/USD caps before execution with current provider pricing; stop at the first exhausted bound. Preserve all attempts/costs. These are configurable defaults, not measured performance claims.
9. Do not claim identical initial deals from equal RNG seeds across implementations. Record observed deal fingerprints and any explicitly controlled randomness. Default to the apps' normal deals, with randomized target order and the same evaluation conditions.

## RQ-6: Reports and evidence

1. Emit machine-readable run JSON, append-only step events, a human-readable static HTML report, and CSV summaries. Retain per-game screenshots, selected gesture videos/traces, runtime errors, model usage, rule verdicts, and artifact digests.
2. Summarize out of ten: verified legal wins, wins with confirmed violations, unverified win claims, unfinished games, app-blocked games, observation/model/actuation failures, infrastructure failures, and unrun/cancelled slots. Separately report games with confirmed rule violations, games with blocked legal actions, and other confirmed bugs. These flags can overlap outcomes.
3. For each violation, show rule ID/text, source/target cards or regions, expected versus actual result, input mode, before/gesture/after evidence, reproducibility status, severity, and links to the exact game/step/build.
4. Distinguish unique defect groups from occurrence counts and affected-game counts. Preserve all occurrences when deduplicating.
5. Keep gameplay clock endpoints separate from setup, artifact rendering/upload, and human review. Report model/tool/wait time and actual usage where available; token estimates remain labeled.
6. Add the gameplay summary to the existing baseball-card dashboard later, beside code KPIs, linked by exact source SHA. Missing/stale/unverified results display N/A/status, never zero bugs or 0/10 wins.
7. Audio, animations, accessibility, and browser support need modality-specific evidence. Screenshots cannot prove sound generation/mute; missing audio capture is `untested`, not pass. Keyboard probes evaluate usability separately from the original product's explicit drag/tap rules.

## RQ-7: Calibration and release gates

1. Test the evaluator against known-good, independently specified browser fixtures and deliberately defective variants. Keep fixture truth/hidden state available only to the fixture judge, never to the visual player.
2. Include false win strings/booleans, unknown counters, animation-only changes, missed gestures, wrong drop targets, partial occlusion, malformed model output, duplicate cards, wrong recycle order, missing reveal, wrong category acceptance, valid moves blocked, score doubling, premature victory, and browser/provider failures.
3. Require evidence-backed detection of every configured critical fixture mutation and zero false confirmed defects on the known-good calibration suite. Report misses/false positives and confidence calibration; do not infer universal accuracy from a finite suite.
4. Demonstrate ten isolated, completely reported legal wins on predeclared solvable known-good fixtures; then evaluate actual generated apps without requiring them to win ten of ten. Every actual result must remain visible, including inconclusive outcomes.
5. Exercise both backends with the same fixture/evaluator contract and prove session cleanup. Unit tests alone do not certify the live visual harness.
6. An unseen compatible layout must work by adding a target manifest entry only. If perception cannot understand it, emit an observation failure with evidence rather than introducing branch-specific code silently.
7. Definition of done: all implementation tasks/gates complete, ten-game reports for at least two independently implemented app branches, passing calibration evidence, no source-state coupling, and documented limitations. This planning commit does not meet or claim those execution gates.
